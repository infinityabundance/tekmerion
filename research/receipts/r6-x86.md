### 2.1 Step derivation on x86

The step numbering had to be re-derived, not reused:

* `define_trimmed` is `TRIM_LIST(4,0)`, so the bound machine code starts after
  the four-byte `ENDBR64`. The tool *requires* exactly that prefix and reports
  trimmed-relative addresses; anything else is refused.
* The `CORRECT` statements may enter after a prologue. P-521's routines push
  callee-saved registers, and the query says `read RIP s = word (pc + 3)`, so
  `STCF` (or `MOV`) is step 1. P-384's routines have no prologue
  (`read RIP s = word pc`), so the first `MOV` is step 1. The entry offset is
  read from the query, not assumed.
* The simulation stops at the last instruction that writes memory. The tool
  checks that the query's postcondition RIP is the address of the **next**
  instruction; a mismatch is refused. This stops before the epilogue
  `POP`/`RET`, which the x86 human proofs also do not simulate.

For P-384 `add` (after trimming): 42 instructions, 41 simulated, final state
`s41`. For P-521 `add`: 45 trimmed, entry 3 (two `PUSH`es skipped), 40
simulated, final state `s40`.

### 2.2 Flag mapping (x86 differs from ARM)

| architecture | after `SUB`/`SBB`/`NEG`/`CMP` | after `ADD`/`ADC` |
|---|---|---|
| AArch64 | `C` is **no borrow** (set iff `minuend >= subtrahend + carry`) | `C` is the carry |
| x86-64 | `CF` is **borrow** (set iff `minuend < subtrahend + carry`) | `CF` is the carry |

The x86 table records the borrow reading explicitly:

```
sub : borrow, set iff val d < val s
sbb : borrow, set iff val d < val s + c
neg : borrow, set iff val d != 0
cmp : borrow, set iff val d < val s
adc : carry,  set iff val d + val s + c >= 2^64
```

The reference route used here does **not** interpret the flag: the accumulator
equations and the reference word function are value-level, and the flag
meaning never becomes a proof obligation. The mapping still matters for the
derivation (`sbb` reads the carry as a borrow, `stc` grounds it, `and`/`or`/`xor`
clear it) and is recorded so that a route which *does* read the flag cannot
silently reuse the ARM assumption.

### 2.3 Simulation shape

Inspected from the x86 proofs (`X86_ACCSTEPS_TAC EXEC anums (range)`, with
`X86_STEPS_TAC` when there is no carry chain). The emitter produces:

```
X86_ACCSTEPS_TAC BIGNUM_ADD_P384_EXEC [2;4;…] (1--41)
X86_STEPS_TAC   BIGNUM_NEG_P521_EXEC (1--39)
```

The accumulate set is derived: `always_link` keeps the final limb of each
add/sub chain even though its carry-out is dead, and `ADC r,r` / `SBB r,r`
materialisations are excluded. `NEG` is dropped from the requested set because
`ACCUMULATE_ARITH_TAC` has no `word_neg` pattern (requesting it is a no-op).

## 4. The two measured encoding defects and their fixes

Both were SATISFIABLE residuals (cadical exit 10), i.e. a bit left free, not an
arithmetic failure.

1. **`NEG` carry.** `NEG`'s CF is `~(x = 0)`, and the form
   `bitval(~(word_neg(word(bitval c)) = word 0))` was left free by BITBLAST.
   All four routines containing `NEG` failed, both routines without it passed.
   Fix: `RULE_ASSUM_TAC(REWRITE_RULE[WORD_NEG_EQ_0; WORD_BITVAL_EQ_0])` before
   the close (the same rewrite the x86 human closes use). After this:
   `add_p384` and `sub_p384` closed; `neg_p384`/`neg_p521` did not.
2. **Zero-test encoding.** BITBLAST does not prove
   `word_join a b = word 0 ==> word_or a b = word 0` (probed directly: SAT,
   0.058 s). The machine tests zero with an OR of limbs; `ref_neg`'s guard is an
   equality on the joined word. Fix: `BRIDGE_NEG_REF_ZERO_TAC` folds both to the
   same limb-wise conjunction via `WORD_OR_EQ_0` and the new generic
   `WORD_JOIN_EQ_0`, with `CONJ_ACI` normalisation so the split hypothesis and
   the mask's condition are syntactically the same. Both `neg` tasks then closed.

The new lemma is generic and curve-free:

```
!x:M word y:N word.
  dimindex(:M) + dimindex(:N) = dimindex(:P)
  ==> ((word_join x y = word 0) <=> (x = word 0 /\ y = word 0))
```

Targeted curve-constant scan (same marker set as
`research/receipts/bridge/curve_check.py`): **CLEAN** (no curve name, no
large numeral, no reduction shape). Whole-file scan: `statements=71 hits=1`,
where the single hit is the pre-existing checker artefact at
`(MOD):num->num->num` (HEAD already reports `statements=68 hits=1`); the new
statements add no hit.

## 6. Memory model and loaded-environment assumption (recorded per task)

**This is a completeness requirement, not a verified result.** The model below
is what the bench and s2n-bignum actually state; it was taken as given and was
not verified by this work.

The model is s2n-bignum's x86 **total-memory** `x86state`: there is no MMU, no
page table, no alignment requirement, and every address is readable/writable.
For **each of the six tasks** the query binds exactly:

* *memory model*: total x86 memory; outputs are little-endian 64-bit limbs via
  `bignum_from_memory (z, N)`; `MAYCHANGE` permits `[RIP; …]`,
  `SOME_FLAGS`, `events`, and `memory :> bignum(z,N)`. No other memory is
  claimed to change.
* *loaded environment*: the routine's bytes are present at `pc`
  (`bytes_loaded s (word pc) (BUTLAST <tmc>)`), the entry RIP is `pc + k`
  (k = 0 for P-384, k = 3 for P-521), and the code segment does not overlap the
  output buffer (`nonoverlapping (word pc, code_len) (z, 8*N)`). There is no
  operating-system, process, stack-alignment or calling-convention assumption
  beyond `C_ARGUMENTS` and the callee-saved set in `MAYCHANGE`; the epilogue
  `POP`/`RET` is not simulated.

| task | locked memory model | loaded-environment assumption |
|---|---|---|
| `add_p384` | s2n-bignum x86 total memory | code at `pc`, RIP entry `pc` |
| `sub_p384` | same | code at `pc`, RIP entry `pc` |
| `neg_p384` | same | code at `pc`, RIP entry `pc` |
| `add_p521` | same | code at `pc`, RIP entry `pc + 3` (two `PUSH`es skipped) |
| `sub_p521` | same | code at `pc`, RIP entry `pc + 3` (two `PUSH`es skipped) |

## 8. DEVELOPMENT_ONLY (transcribed, named, not claimed)

1. **`simulation.accsteps`** — one `X86_ACCSTEPS_TAC` block over the whole
   routine is the x86 human proofs' idiom; the step set is derived. `NEG` is
   dropped from the requested set.
2. **`simulation.entry`** — skipping the `PUSH` prologue follows the query's
   RIP offset; reading that as an executable entry is taken from the x86 proof
   style.
3. **`post.neg_flag_rewrite`** — `WORD_NEG_EQ_0`; `WORD_BITVAL_EQ_0` is copied
   from the x86 human closes, and is emitted only for routines containing `NEG`.
4. **`post.zero_test_fold`** — `BRIDGE_NEG_REF_ZERO_TAC` (the fold itself is
   generic; the decision to use it for `NEG` routines is transcribed).
5. **`post.digit_expansion`** — `BIGNUM_EXPAND_CONV`/`BIGNUM_LEXPAND_CONV`,
   the `LAND_CONV`/`RAND_CONV` traversal and `DISCARD_STATE_TAC`.
6. **`post.bitval_rewrites`** — `RULE_ASSUM_TAC(REWRITE_RULE[REAL_BITVAL_NOT;
   ADD_CLAUSES; VAL_WORD_BITVAL])` in the add close.
7. **`--mode dev`** reads the `define_assert_from_elf` word list and the modulus
   definition out of `x86/proofs/bignum_{op}_{family}.ml` for a scratch process.
   The judged answer does not: it uses the benchmark setup's own definitions.
8. **`always_link`** is a policy choice, documented in `derive_steps.py`, not a
   fact read from a proof: the top limb's carry-out is dead but its digit-sum
   relation is still requested.

## 9. What is still wrong / not claimed

* This is a **development** result on six tasks. It says nothing about the nine
  sealed counterparts, and it is not a coverage claim over x86.
* The two encoding defects in §4 are fixed by *named, transcribed* rewrites and
  a new generic lemma. They are not a general solution: a routine whose zero
  test or flag is encoded in a shape BITBLAST still cannot see, and that is not
  covered by `BRIDGE_ZERO_TEST_TAC`, will still come back SATISFIABLE. No such
  routine was found in the declared set, but none was searched for.
* `BRIDGE_JOIN_ZERO_CONV` discharges the width side condition with a fixed
  conversion; it is guaranteed by the `word_join` construction in
  `bridge_word_width`, but it is not proved as a standalone obligation.
* `add_p521` is the slowest at 62.8 s (0.52 of budget). The route is not free;
  a larger limb count raises the SAT cost.
* The x86 `CORRECT` statements skip the prologue and stop before the epilogue.
  The `SUBROUTINE_CORRECT` statements that cover the full calling convention
  were not attempted.
* Python 3.14.10: `combine-answer-and-setup.py … 1` (one core). Multi-core
  crashes on this Python, as recorded in R4.
